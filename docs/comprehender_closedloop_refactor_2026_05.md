# Comprehender + Closed-loop refactor — 2026-05

Seventh in the 2026-05 refactor series. Paired with the explicit
goal of finding **defects**, not just observability gaps. The user
flagged this pair specifically because of the global-correctness
risk: comprehender feeds Prototyper context, closed-loop drives
multi-iter automaton evolution; bugs in either cascade through the
whole pipeline.

Three core design questions surfaced during review — user
confirmed all three recommendations. Five secondary defects also
fixed in the same commit.

The "empirical validation" section is intentionally blank.

---

## §1. Core design decisions (Q1–Q3, user-confirmed)

### Q1: closed-loop docstring promised L4 re-rank that implementation never delivers

**Symptom.** Module docstring §3 claimed:
> "Re-runs L4 ``select_top_k_sequences`` with the updated automaton — the
> acceptance score, sample paths, creator-grafts, and Phase E post-parse
> extensions all read the grown PTA."

Implementation: `run_closed_loop` calls `resynthesize_fn(artifact, K)` —
an opaque callable. The production wiring in `data_context.py:1140`
passes `_resynth = _generate_cbfactory_drivers`, which uses
`factory.create_random_driver_skeleton()` (random walk). **`select_top_k_sequences` is never re-invoked per-iter.** Only CBFactory's Phase H
`AutomatonAcceptanceGuard` reads the artifact (hard-prune by
acceptance threshold). The four richer L4 signals (acceptance as
sort axis, sample_accepting_paths injection, graft_creator_prefix,
post_parse_extensions) are dormant in the closed-loop path.

**Decision: update docstring to match implementation** (not the
other way around). Rationale that drove the choice:

  - Implementing the L4 re-rank would make consecutive iterations
    produce **identical** deterministic top-K (no novelty in
    evidence → automaton saturates instantly → closed-loop
    degrades to a single iter). The random-walk's per-iter
    diversity is what keeps the automaton evolving across rounds.
  - "Make impl match docs" would be a textbook example of
    *local-optimal-that-degrades-global* — a fix that looks
    correct but breaks the multi-iter design.
  - Future work: a "weighted random sample from L4 top-K +
    sample_paths injection" hybrid could provide L4 signal use
    *and* per-iter diversity. Defer until we have empirical data
    showing the current random walk under-uses the automaton.

**File.** `src/closed_loop.py:1` (module docstring).

### Q2: Comprehender-B's automaton prefilter had no strength gate

**Symptom.** `comprehend_sequences` short-circuits to `VALID`
(skipping the LLM call) when `acc >= 0.999`. Same `acceptance_score`
the L4 ranker uses — but L4 wraps the call in
`AutomatonAcceptanceGuard.is_strong()` to ignore weak automatons.
Comprehender-B did NOT have this gate. Result: early-iter weak
automatons could give false-positive `acc=1.0` on short sequences
whose APIs happened to be observed early — Comprehender-B would
prematurely declare them `VALID` and skip semantic LLM scrutiny.

**Decision: add the strength gate** (mirrors L4's policy). New
module-level helper `_automaton_is_strong(acceptance_fn)`:

  - Pulls the artifact off the bound method (`__self__`).
  - Wraps it in `AutomatonAcceptanceGuard` and reads `is_strong()`.
  - On any introspection failure → returns `True` so we don't
    accidentally disable the prefilter for unfamiliar callable
    shapes; the downstream LLM call is the correctness safety net.

The prefilter now only runs when the gate accepts. Empirical
effect: late-iter (strong automaton) → savings as before; early
iter (weak automaton) → no false-VALID labels.

**File.** `src/knowledge/comprehender.py:_automaton_is_strong` (new),
`comprehend_sequences` (gate added before prefilter block).

### Q3: `patched_sequence` advisory vs apply

**Symptom.** When Comprehender-B classifies a sequence as
`SUBOPTIMAL`/`INVALID` and emits a `patched_sequence`, the
production path includes it as prose advisory in the Prototyper
prompt only. No code replaces the original sequence with the
patch in the skeleton-synthesis pipeline.

**Decision: keep advisory** (current behaviour). Rationale:

  - Apply path requires re-validating the patched_sequence through
    L4's full filter chain (type / lifecycle / state-machine + Z3
    acceptance). The patch is generated by an LLM with weaker
    constraint awareness than L4. Risk of replacing
    `original viable` with `patched unviable` is non-trivial.
  - The advisory format leaves the choice to the LLM (Prototyper),
    which sees both the original sequence and the suggested fix.
    If the fix is genuinely better, the LLM will use it.
  - No empirical evidence yet that apply outperforms advisory.
    Defer the harder fix (apply + re-validate) until we have data.

**No code change** for this item.

## §2. Secondary defects fixed in this commit

### CL2 — Dead `guard_pruned` / `guard_passed` metrics

Both fields lived in `IterationRecord` but the closed-loop had no
handle to the production `Z3GuidedSynthesisController.automaton_guard`
(it's per-CBFactory-instance, instantiated inside the caller's
`resynthesize_fn`). The probe guard created locally was never fed
candidates; both metrics always reported 0.

**Fix.** Dropped both fields from `IterationRecord` and the
metric-recording block. Kept `automaton_strong` and `guard_threshold`
which DO reflect the artifact's state at end of each iteration.
Reporting 0 forever is worse than reporting nothing.

### CL5 — Persistence only at end-of-run

`closed_loop_trajectory.json` was written only after the final
iteration. A crash in iter N lost the trajectory of iter 1..N-1.

**Fix.** Persist after each iteration. A long closed-loop run is
now partially recoverable from disk if it dies mid-flight.

### C2 — Greedy regex in `_extract_json_block` fallback

`_extract_json_block` first tries to find a fenced ``` ```json block,
falling back to `re.search(r"\{.*\}", text, DOTALL)`. The fallback
regex is greedy — when an LLM response contains multiple JSON
objects separated by prose, it captures everything from the first
`{` to the **last** `}`, including arbitrary text in between.
`json.loads` then chokes.

**Fix.** Replaced the greedy regex with a quote-aware balanced
bracket scanner (`_first_balanced_json`). Returns the first
complete top-level object or array; correctly handles nested
braces and quoted strings.

### C4 — `comprehend_purpose` cached the generic fallback

When the LLM returned empty (transient failure / rate limit /
provider down), the function fell back to a generic template
`"<name>: a C/C++ library; ..."` AND wrote it to
`results/<project>/comprehension/purpose.txt`. The next run read
the cached template and never retried the LLM.

**Fix.** When falling back, return the template but **don't
write to cache**. Next run retries.

### C5 — `_llm_fill_api_usages` dropped entire batch on parse failure

If a batch's LLM response was unparsable (10 APIs at a time), the
function logged a warning and `continue`d to the next batch. The
10 APIs in the failed batch ended up with no usage at all —
Prototyper saw `"(no usage available)"` for each of them, losing
the static-fact signal we already had cheaply.

**Fix.** On batch parse failure, write a signature-only fallback
for every API in the batch (`"signature: <sig> (usage detail
unavailable; LLM call failed)"`). Same treatment when the LLM
parses successfully but omits a specific API entry.

## §3. Other observations from the review

These were noted but didn't trigger a code change:

  - **CL3** (default no-preflight): docstring matches behaviour. Not
    a defect; the trade-off is documented.
  - **CL4** (`drivers_so_far` accumulates across iters): caller
    receives the union of all iters' drivers. Intentional per the
    "more evidence = more drivers" design.
  - **CL6** (resynth exception → empty driver list): loop terminates
    via the saturation early-stop (no new evidence → no automaton
    change → Δ=0 streak hits cap). Not infinite.
  - **C7** (cache content-hashing): per-project layout is correct.
    `api_usage.json` and `purpose.txt` are NOT content-hashed; if
    project APIs change across runs, stale usage entries silently
    persist. Defer — empirical question whether this matters
    (the cache key is the API NAME, so renamed APIs do invalidate;
    only signature changes for same-name APIs would leak stale
    descriptions, rare in practice).

`docs/comprehender_closedloop_refactor_2026_05.md` is the

## §5. Rollback recipe

- Q1 docstring: revert the §3 paragraph to the original promise
  text.
- Q2 strength gate: drop the `_automaton_is_strong` helper and
  remove the guard from the `if automaton_acceptance_fn` branch.
- CL2: re-add `guard_pruned` / `guard_passed` to `IterationRecord`
  with always-0 values.
- CL5: move the persist block back to the post-loop position.
- C2: restore the greedy regex fallback.
- C4: re-add the `self.cache.save_purpose(...)` line in the
  fallback branch.
- C5: drop the signature fallback in the parse-failure and
  missing-entry branches.
